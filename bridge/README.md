# Marshal bridge

Marshal (CLI: `lotse`) lets you watch and steer your coding agents from a Meta Quest headset. This bridge runs on your PC. It receives Claude Code hook events (and those of Muse, Codex CLI, Gemini CLI and OpenCode, see "Other agents") on `127.0.0.1:47820` and forwards them over WebSocket (`0.0.0.0:47821`) to the headset app. The command you type, the `~/.lotse` folder and the `LOTSE_*` variables keep the name `lotse`.

## Quick start

1. Once, in `bridge/`: `npm install` and `npm run build`.
2. `node dist/cli.js connect`. It lists, for every agent it finds on this computer (Claude Code, Muse, Codex CLI, Gemini CLI, OpenCode), the file it changes and the entries it adds, asks once (`--yes` skips the question), installs, and starts the bridge. To remove everything again: `node dist/cli.js disconnect`. For one project folder only: `connect --project <dir> [--tool muse|codex|gemini|opencode] [--temporary]`.
3. In the headset: open Marshal and look at the QR code in the terminal (or choose "Connect to my PC" and enter the code shown). Then work as usual, also in the Claude desktop app. The steps for a juror: `docs/setup.md`.

## CLI

Requires Node.js 22.12 or newer (`engines` in `package.json`; developed on Node 22.17.0). Build once with `npm run build`, then run `node dist/cli.js <command>` from `bridge/`.

- `connect --project <dir> [--tool claude|muse|codex|gemini|opencode] [--transport command|http] [--temporary] [--budget 15] [--explain cli|off] [--no-browser]` is the one command for a real session. It installs the hooks like `install-hooks` (idempotent: Marshal's own hooks are replaced, foreign hooks are still refused, there is no `--force`), then starts the bridge like `start` (`--explain` as there: `cli` when `claude` is on PATH, else `off`) and prints one framed block with the pairing code, every LAN address, the pairing QR code (see "Pairing QR code") and "In the headset: open Marshal and look at this code." (without a QR code: "In the headset: Connect to my PC"). With `--temporary` the hooks are removed again on Ctrl+C (and when the bridge cannot start), but only if this run installed or changed them: hooks that were already there exactly so stay. Without it they stay until `uninstall-hooks`. If `LOTSE_TOKEN` is set in this shell but differs from `~/.lotse/token`, it warns: hooks of sessions without `LOTSE_TOKEN` (the Claude desktop app) read the file.
- `connect [--all] [--tool claude|muse|codex|gemini|opencode|all] [--yes] [--keep-muse] [--budget 15] [--explain cli|off] [--no-qr] [--no-browser] [--host <ipv4>]` and `disconnect [--all] [--tool …] [--yes]`: the hooks for all sessions of the user, in the user-level files of the tools (see "All sessions"). Without `--project`, `connect` and `disconnect` are this mode, so `lotse connect` with no flags is the one-command setup; `--all` is still accepted.
- `start [--record <file> [--force]] [--budget 15] [--explain cli|off] [--no-browser]` starts the bridge, prints the 6-digit pairing code and the LAN IPv4 addresses, and optionally records anonymised events. The recording file is opened only after the ports are bound, and an existing file is refused unless `--force` is given. SIGINT, SIGTERM, SIGHUP and SIGBREAK close the recorder, then the server (exit code 1 if either fails), and print a reminder to run `uninstall-hooks`. `--budget` (USD) raises a `budget_near` incident once per session at 70% of the budget and a `budget` incident when the budget is reached.
- `demo <recording.ndjson> [--speed 1] [--root <dir>] [--budget 15] [--explain cli|off]` serves a recording to the headset as if live. It prints "Waiting for the Quest to pair ..." and starts the replay only after the first successful pairing, so the headset sees it from the first event. Permission requests in it open real broker requests that resolve locally. A recording with a malformed line or a wrongly typed field is refused with its line number; an event that fails during the replay is skipped with one log line.
- `pack <recording.ndjson> -o <pack.json> [--overrides <file>] [--budget 15] [--explain cli|off]` turns a recording into an offline demo pack for the Quest app (see "Demo pack" below). `--explain` defaults to `off` here.
- **Pairing QR code.** `connect`, `start` and `demo` show a QR code under the pairing code when stdout is a terminal at least as wide as the code (41 columns for the usual payload); the headset can pair by looking at it instead of the user typing the address and the code. `--no-qr` switches it off. It is never shown when stdout is not a terminal (a pipe or a log file), so it never lands in a log. The payload is exactly `marshal://pair?v=1&h=<host>&p=<ws port>&c=<6-digit code>` and nothing else (no token, no user name, no host name, no path). `<host>` is only ever a private RFC 1918 address (10/8, 172.16/12, 192.168/16) on a network adapter whose name does not mark it as virtual or a VPN (vEthernet, WSL, Hyper-V, VirtualBox, VMware, Docker, Tailscale, ZeroTier, WireGuard, TAP, TUN, Loopback; case-insensitive); never link-local 169.254/16, CGNAT 100.64/10, loopback or a public address. Of those, the one the OS would use for the default route (a UDP socket "connected" to the documentation address 192.0.2.1 picks the route; no packet is sent), else the first. It is listed first and marked "<- in the QR code" when there are several addresses. If no address passes, there is no QR code and the block says why. `--host <address>` (`connect`, `start`, `demo`) chooses it by hand; it accepts only a literal private IPv4 address. The code in the QR code is the same one-time code printed in clear next to it, with the same lifetime (5 minutes) and attempt limits. The QR block is printed last, below the frame. When its code is used (a headset paired), expires or is replaced (Enter), the block is erased from the terminal if nothing else was printed since (cursor up and erase; terminal only), and one line says "The pairing code shown above is no longer valid (…)"; a new code gets a new QR block. The encoder is `src/qr.ts` (byte mode, level M, versions 1 to 6, mask by the standard's penalty rules, Reed-Solomon over GF(256)); it has no dependency. Each cell is an upper half block (two modules per line) with explicit black and bright-white colours and a 4-module quiet zone, so it reads on dark and light terminal themes.
- **Status page in the browser.** `connect` and `start` print `Open in your browser: http://127.0.0.1:47820/ui?k=<key>` near the top and open that page with the system browser (Windows `start`, macOS `open`, Linux `xdg-open`), unless `--no-browser` is given, stdout is not a terminal, or `CI` is set. The page shows the pairing QR code and the code with its 5 minutes counting down, a "New code" button (same as Enter: the previous code stops working, the terminal shows the new one), and once paired the agents, the waiting requests and the explanation mode. It is one self-contained file (no external fonts, scripts or images) that polls `GET /ui/state` once a second. The key is 32 random hex characters, new for every bridge process, and stands in for the token, which the browser does not have. It works once, for loading the page: the browser was started with it on its command line, where other local processes can read it. That load sets an HttpOnly, SameSite=Strict cookie (`marshal_ui_<port>`, path `/ui`) with a second secret, which the page's requests and any reload in that browser use; the page also removes the key from its address. Without a valid cookie, a used, wrong or missing key answers 404 like any unknown path. The Host must be `127.0.0.1:47820` or `localhost:47820` (DNS rebinding), an Origin, when sent, must be the page's own (`POST /ui/code` from another site is refused), there are no CORS headers, and the answers carry `Cache-Control: no-store`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a CSP that allows nothing from elsewhere. The state never contains the ingest token. `/ev`, `/perm`, `/status` and `/reply` still need `X-Lotse-Token`; the key does not replace it. `demo` and `pack` have no status page.
- In `start` and `demo`, pressing Enter prints a fresh single-use pairing code (the previous one stops working), for example when the code has expired or a pairing attempt burnt it. While all agents are halted (see "Halt all"), the line `continue` (the older `weiter` still works) instead releases the halt (only when stdin is a terminal). There is deliberately no CLI or HTTP command to release a halt.
- `statusline` reads the statusline JSON on stdin, POSTs it to `/status` and prints `Marshal · <ctx>% · $<cost>` (`Marshal` alone when ctx or cost is missing). Reading stdin and the POST share one deadline of 500 ms, counted from process start. It never fails Claude's status line: errors are swallowed and the exit code is always 0.
- `hook --source claude` is the command hook Claude Code runs for every event (see "Claude Code: command hooks" below); `hook --source muse|codex|gemini|opencode` is the command hook of the other agent CLIs (OpenCode: run by Marshal's OpenCode plugin) (see "Other agents" below). A bare `hook` counts as `--source claude` (older installs use it for SessionStart). The approval hook of each tool also names its event (`--event PermissionRequest`, Gemini `--event BeforeTool`). Observe-only events go to `/ev` within the 500 ms deadline, counted from process start, and print nothing (Claude would take that stdout as context). Approval hooks wait up to 10 s for their stdin (also an older install without `--event`, once the part of stdin that arrived shows a permission event), so a loaded machine does not lose them. It swallows every error and always exits 0. The `hook` process loads only the shim, never the bridge server. `LOTSE_HTTP_PORT` overrides the bridge port 47820 for `hook` and `statusline` (used by the tests).
- `install-hooks --project <dir> [--tool claude|muse|codex|gemini|opencode] [--transport command|http] [--force]` writes the hooks for the chosen tool (default `claude`; the other tools are described under "Other agents"). For Claude it writes the hooks and the `statusLine` into `<dir>/.claude/settings.json` only; `--transport` picks command hooks (default) or the older http hooks (Claude only). It is idempotent: hooks that are exactly Marshal's own for this CLI (either transport) are replaced, and nothing is written when the file already has exactly these hooks. It refuses any other existing `hooks` or `statusLine` unless `--force` is given, and a settings file that is not a JSON object. `--force` replaces the whole `hooks` object (including unrelated hooks that were already there) and the `statusLine`; every other key stays. It refuses, checked again right before the write, with the file opened without truncation so its identity can be compared first:
  - a missing directory, and on Windows any UNC or device path (starting with \\);
  - the home directory: same real path (compared case-insensitively on Windows, with a `\\?\` prefix stripped), or same file identity (device and inode);
  - a `.claude` that is a link, resolves to `~/.claude` (or to `CLAUDE_CONFIG_DIR` when that is set), or has the same identity;
  - a `settings.json` that is a symlink or has the same identity as `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR/settings.json`);
  - any case where one of the paths cannot be resolved (it fails closed).
  Not covered: a hard link to a file outside these locations, or a change made between the final check and the open by a process that is faster than the check.

  **Do not commit the `.claude/settings.json` that `install-hooks` writes.** Its `hook` and `statusline` commands contain the absolute local path to `dist/cli.js` on your machine. Run `uninstall-hooks` before committing, or keep the file out of version control.
- `uninstall-hooks --project <dir> [--tool claude|muse|codex|gemini|opencode]` runs the same checks, then removes only entries that are exactly what `install-hooks` writes for this CLI, for both Claude transports (the command hooks `node "<this dist/cli.js>" hook --source claude`, the http hooks to `http://127.0.0.1:47820/ev` and `/perm` carrying `X-Lotse-Token`, `node "<this dist/cli.js>" hook` and `statusline`). Every other key, hook and statusLine stays. It does not write when nothing was removed.

### Claude Code: command hooks

By default `install-hooks` (and `connect`) give Claude Code a `type: "command"` hook for every event, PermissionRequest included (timeout 120 s): `node "<dist/cli.js>" hook --source claude` (PermissionRequest: `… hook --source claude --event PermissionRequest`). The hook reads the token itself (`LOTSE_TOKEN`, else `~/.lotse/token`), so it also works where Claude sessions have no `LOTSE_TOKEN`, as in the Claude desktop app.

- A PermissionRequest waits for the headset (the bridge holds it 90 s, the hook waits up to 100 s). An allow from the headset prints `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`, a deny the same with `"behavior":"deny"` and its message.
- Without a headset decision (bridge off, wrong token, no headset paired, hold timeout, any error) the hook prints nothing and exits 0. Claude Code then shows its normal permission dialog, as documented for hooks that make no decision.
- Claude's own permission rules (and other automatic approvals) stay as they are: only requests that Claude still asks about reach the hook.
- `--transport http` installs the older http hooks instead; those need `LOTSE_TOKEN` in the environment of every Claude session (see "Token setup").

### Token setup

Every HTTP request to the bridge must carry `X-Lotse-Token`. `start`, `connect` and `demo` read `LOTSE_TOKEN` from the environment, or else `~/.lotse/token` (created on first use, 32 random bytes as hex). The command hooks read it the same way, so with them nothing needs to be set. Only the http hooks (`--transport http`) need it in the environment: those settings reference `$LOTSE_TOKEN` (`allowedEnvVars`), and the token itself is never written to a settings file. Set it in the shell that runs `claude`:

- PowerShell: `$env:LOTSE_TOKEN = (Get-Content "$HOME/.lotse/token").Trim()`
- bash: `export LOTSE_TOKEN="$(cat ~/.lotse/token)"`

**Pairing is LAN-only and unencrypted (ws://); use it only on a network you trust. The code is single-use and expires after 5 minutes.**

### Hooks are only active while you use Marshal

Hooks are active only while you use Marshal; run `uninstall-hooks` when you stop. On shared machines another local user could bind port 47820 while the bridge is not running, and would then receive the hook events and the token (and could answer `/perm` with allow). The threat model is a single-user development machine. A `/perm` that is unreachable or answers `{}` falls back to the normal Claude Code prompt (no decision).

## Other agents

Besides Claude Code, **Muse** (Meta, `muse-code`), **OpenAI Codex CLI** and **Google Gemini CLI** also report their agents to the bridge. None of the three can do HTTP hooks, so each calls a command hook, `node "<dist/cli.js>" hook --source muse|codex|gemini`. This shim reads the hook JSON from stdin, translates it into the Claude Code names (events, shell tool, path fields) and sends it to `/ev` or, for an approval, to `/perm`.

| Tool | Visible on the Quest | Approval from the Quest | Project file |
|---|---|---|---|
| Muse 1.4 | yes, as "Muse N" | allow and deny (`PermissionRequest`); **without a headset decision it is denied** | `<project>/.muse/hooks.json` |
| Codex CLI 0.164 | yes, as "Codex N" (no `Notification` event) | allow and deny (`PermissionRequest`) | `<project>/.codex/hooks.json` |
| Gemini CLI 0.41 | yes, as "Gemini N" | **deny only** (`BeforeTool`): Gemini still asks itself; Marshal can only deny, and also sees calls that Gemini would otherwise allow automatically. The headset shows "Deny only" as the block's instruction line (from the agent's source); the explanation itself carries no vendor prefix | `<project>/.gemini/settings.json` (only the `hooks` key) |
| OpenCode 2.3 (V2 plugin API), **not checked live** | yes, as "OpenCode N" (the headset lists it under "Other agents") | allow and deny (`permission.evaluate`, only what OpenCode would ask about); without a headset decision OpenCode asks as usual | `<project>/.opencode/plugins/marshal/index.js` (a plugin file, no hooks) |

- **Installing.** `node dist/cli.js install-hooks --tool muse|codex|gemini --project <dir> [--force]`, remove with `uninstall-hooks --tool … --project <dir>`. Without `--tool`, `claude` applies as before. The same safety rules as for Claude apply: only an existing project folder, no home directory, no UNC path, and the tool folder in the project may be neither a link nor one of the user folders (`~/.muse`, `~/.config/muse` and `$XDG_CONFIG_HOME/muse`, `~/.codex` and `CODEX_HOME`, `~/.gemini` and `$GEMINI_CLI_HOME/.gemini`). Existing `hooks` are not overwritten without `--force`; `uninstall-hooks` removes only entries whose command is exactly this CLI's shim for this tool. The approval hooks get a 120 s time limit (Muse and Codex in seconds, Gemini in milliseconds). As with Claude: the written file contains the absolute path to `dist/cli.js`, so do not commit it.
- **One-time step in the tool** (`install-hooks` prints it): Muse runs project hooks only in a trusted folder (trust the folder on the first start there, and the new hooks too). Codex loads project hooks only when the project is trusted, and every hook must be confirmed once in `/hooks` (again after every change). Gemini needs a trusted folder and asks about new or changed project hooks.
- **Token.** The shim takes `LOTSE_TOKEN`, else `~/.lotse/token`. Muse clears the environment of its hooks down to a few variables, so there the file counts.
- **Muse and Codex.** `PermissionRequest` waits for the Quest (the bridge holds 90 s, the shim waits up to 100 s). If the Quest allows, the shim prints `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`; if it denies, the same with `"behavior":"deny"` and a `message` that is never empty. All other events are observation only. Muse's shell tool (`shell`) runs in PowerShell on Windows and is therefore classified by the PowerShell rules, otherwise by the bash rules. On Windows every command from Muse, Codex or Gemini gets the bash **and** the PowerShell rules, and the worse counts: even a tool called `Bash` (Muse's compatibility name, Codex) runs in PowerShell there (so `Set-Content ..\x.txt` and `echo hi > ..\x.txt` are destructive). The PowerShell short forms `sc`, `ac`, `clc`, `mi`, `rni`, `cpi`, `sp`, `si` as well as `Tee-Object`, `tee`, `Export-Csv`, `Export-Clixml`, `Set-ItemProperty` and `Set-Item` count as writing commands. Claude commands keep their own dialect. A Codex `exec_command` carries its command line in `cmd`; the shim also stores it as `command`, so that the shell rules read it and the card shows it. An unknown tool from Muse or Codex without a command and without a path field is "Unclear tool", so destructive (two hands). A Codex `apply_patch` is classified by its file header lines (`src/risk/patch.ts`), never by the shell rules; the patch text stays in `command` and appears shortened on the card. This applies only to requests from Codex: a tool called `apply_patch` from Claude, Muse or Gemini gets the general rules (shell, paths, tool name). For Codex too, the general name and path checks run alongside, and the worse counts; any input field other than `command` makes the patch unclear, so destructive. The parser fails closed: any line that (after trimming) starts with `***` and is not a known header line (`Begin Patch`, `End Patch`, `End of File`, `Add`/`Update`/`Delete File:`, `Move to:`) makes the patch destructive ("Unclear patch"), as do no files or more than 5. A delete is always destructive, and so is a target outside the project. Whitespace and CRLF around the header lines are tolerated.
- **Gemini, deny only.** Gemini has no approval hook, and an `allow` from `BeforeTool` does not skip Gemini's own confirmation. A `BeforeTool` that the classifier does not rate `safe` therefore goes to the Quest as an approval request: Deny prints `{"decision":"deny","reason":…}` and Gemini does not run the tool; Allow or no answer prints nothing, and Gemini then asks in the terminal as usual. `safe` tools are only observed. `run_shell_command` runs in PowerShell on Windows and is classified as for Muse; `read_file`, `write_file`, `replace` and so on are classified like `Read`, `Write`, `Edit`.
- **Muse: without a headset decision it is denied.** One source says Muse treats an empty output on `PermissionRequest` as allow. Until a live test disproves this (`MUSE_EMPTY_STDOUT_IS_ALLOW = true` in `src/adapters.ts`), the shim answers every Muse approval without a decision (bridge off, wrong token, no Quest paired, time limit, `{}` from the bridge, unreadable JSON, any error) with `deny` and the message `Marshal: no decision from the headset, so this is denied. The user can decide again.`. Muse then does not ask by itself; to work without the Quest, remove the hooks (`uninstall-hooks --tool muse`). All other Muse events stay silent.
  - The approval hook is `hook --source muse --event PermissionRequest`. With this switch every path without a headset decision prints the `deny`: empty, late or cut stdin, unreadable JSON, an event other than expected, wrong or extra arguments, and any error. The `deny` lives in `src/hook-fallback.ts`, which is loaded first and imports nothing else (so the product name is spelled out there; a test keeps it in step with `PRODUCT_NAME`). `--source=muse` and `--event=PermissionRequest` work like the form with a space; an `--event` without a value counts as the approval hook for Muse, so `deny`.
  - **Reinstall hooks that were installed before the `--event` switch:** `lotse connect --project <dir> --tool muse` (or `install-hooks`) replaces its own hooks without `--force`. Until then, for such old Muse hooks (`MUSE_SESSION_ID` set, no `--event`): the bridge waits up to 10 s for stdin, and empty or late stdin counts as an approval without a decision, so `deny`. The same holds for Claude, Codex and Gemini: reinstall, so that the approval hook gets its switch.
  - If `MUSE_SESSION_ID` is set (Muse keeps this variable in the hook environment), the call counts as Muse, whatever `--source` says.
  - Cannot be avoided: if `dist/` is missing (not built, deleted) or Muse aborts the hook itself (its own time limit shorter than the shim's 100 s), no Marshal code runs any more and nothing is printed. The live test has to settle this; without the Quest, remove the hooks.
- **Codex and Gemini fall back silently.** Bridge off, wrong token, no Quest paired, time limit, broken JSON or unknown arguments: the shim prints nothing and exits 0, and the tool shows its own prompt. It prints an `allow` only when the bridge answered `allow` for exactly this request. Exit 2 (which would block in all three tools) never happens.
- **OpenCode.** OpenCode has no command hooks, so Marshal writes a small plugin (`src/opencode-plugin.ts` generates it; plain JS, no imports besides `node:child_process`): `<config>/opencode/plugins/marshal/index.js` for all sessions (`<config>` is `$XDG_CONFIG_HOME`, else `~/.config`, also on Windows) or `<project>/.opencode/plugins/marshal/index.js` with `install-hooks --tool opencode --project <dir>`. For each event it starts `"<node>" "<dist/cli.js>" hook --source opencode [--event PreToolUse|PermissionRequest]` with a small JSON on stdin (`{event, sessionID, cwd, tool?, input?, status?, action?, resources?, error?}`) and reads its stdout:
  - `tool.execute.before` sends PreToolUse (waits up to 3 s); the shim's `{"decision":"deny","message":…}` (halt-all) makes the plugin throw, which blocks the call. So OpenCode counts as `every-step` for the halt.
  - `permission.evaluate` sends a PermissionRequest only when OpenCode would ask (`effect: "ask"`), joined by the call id to the tool call seen in `tool.execute.before`, and waits up to 105 s (the bridge holds 90 s, the shim 100 s). `{"decision":"allow"}` (printed only for exactly an allow) sets the effect `allow`, a deny sets `deny` with its message; anything else (no headset, timeout, bridge off, unreadable output) leaves the effect alone, so OpenCode asks in its own prompt. The plugin never throws there.
  - `tool.execute.after`, `session.created`, `session.status` (idle: Stop), `session.execution.failed` and the plugin's end are sent as observe-only events (2 s, fire and forget).
  - Tools: `shell` becomes `PowerShell` on Windows, else `Bash` (on Windows both rule sets apply, as for Muse); a `workdir` other than the session folder makes the call unclear (two hands). `edit`, `write`, `read` become `Edit`, `Write`, `Read` with `file_path`. `patch` (`patchText`) becomes `apply_patch` and is read by the same fail-closed parser as the Codex patch (a delete, an unknown header line or any other input field is destructive). Other tools without a command or path are "Unclear tool".
  - A permission request without its joined tool call is shown from its action and resources: a read of exactly one file as `Read`; everything else (shell sub-commands, edit files, other actions) is marked unclear, so two hands, because OpenCode's parsed list can look safer than the call that runs.
  - Installing: the same guards as the other tools (an existing project folder, no home directory, no UNC path, `<project>/.opencode` neither a link nor OpenCode's user folder); in addition no folder on the way to `index.js` and not the file itself may be a link. A file that is exactly the plugin for this CLI is replaced or removed; an older Marshal plugin (first line `// Marshal plugin for OpenCode, generated by Marshal.`) is replaced after a backup next to it; any other file there is refused (project mode: `--force` backs it up and replaces it). Removing deletes only exactly this CLI's plugin, and then its folder `plugins/marshal` if it is empty. OpenCode loads plugins at start: restart it after `connect`.
- **Not checked live.** No agent of the four tools was started (OpenCode: the plugin API comes from OpenCode 2.3.0's source; that a throw in `tool.execute.before` blocks the call and that `permission.evaluate` is awaited before the prompt is taken from there, not tried). The payloads come from the docs, from strings in the Muse binary and from third-party captures (see `docs/research/2026-11-11-other-agents-hooks.md`). Check before the demo: that Muse loads `.muse/hooks.json` and accepts `timeout: 120`, whether an empty output on `PermissionRequest` means "no decision" or "allow" for Muse (only then may `MUSE_EMPTY_STDOUT_IS_ALLOW` become `false`), which value `hook_event_name` carries for Muse (the shim accepts camelCase and PascalCase), and how Codex behaves when the hook runs into its time limit.

## All sessions

`connect --project` applies to one project folder. For all sessions (every project, every terminal, the Claude desktop app) there is the global mode, which is also what `connect` with no flags does:

- **Switching on:** `node dist/cli.js connect [--all] [--tool claude|muse|codex|gemini|opencode|all] [--yes] [--keep-muse]`. Without `--tool` all five tools apply; a tool whose user folder is missing (so it is not installed) is then skipped ("not found"). With `--tool <one>` the folder is created.
  - The command first shows exactly what it changes: per file the path, then every entry it removes (`-`, older Marshal handlers and an old Marshal status line included) and adds (`+`), as JSON, exactly what is then written; for Muse the user plugin and its events. Then it asks once in the terminal: `Install Marshal hooks globally for: … ? [y/N]`. Only `y`, `yes`, `j` or `ja` go on; anything else (also Enter or a closed stdin) cancels without writing anything. `--yes` skips the question (for scripts). When stdin is not a terminal and `--yes` is missing, it does not ask, changes nothing, says "No terminal to ask on, so nothing was changed. To install without the question: lotse connect --yes" and exits with 1 without starting the bridge. If everything is already installed, it does not ask and writes nothing.
  - After the answer, Marshal plans the files again. If a file changed since it was shown, nothing is written ("changed during the question, nothing written"). If a write fails, Marshal restores the files already written in this run, names them, and the bridge does not start. Errors and refusals go to stderr.
  - Then the bridge starts exactly as with `connect`: pairing block, explanation AI, Enter for a new code. The hooks of Claude, Codex and Gemini stay installed after Ctrl+C. **Marshal removes the Muse plugin again on exit** (Ctrl+C or normal end; at the start it says "The Muse hooks are removed again on exit"), because without a running bridge Muse denies every approval. `--keep-muse` keeps them. If the bridge crashes, they stay and Muse denies (the safe direction).
- **Switching off:** `node dist/cli.js disconnect [--all] [--tool …] [--yes]` lists every entry it removes (file by file, as JSON) and asks once in the terminal, like `connect`; `--yes` skips the question, and without a terminal and without `--yes` it changes nothing and exits with 1. `uninstall-hooks --project <dir>` does the same for one project. **While Marshal is halted** (the marker `~/.lotse/halt` exists, or a bridge on the hook port says it is halted) both refuse, with or without `--yes`: "Marshal is halted, so its hooks stay. Release the halt first, from the headset or the bridge console." When nothing else changed the files in between, they are byte for byte what they were before `connect` (the matching backup is copied back; a file Marshal created is deleted). What stays: the backups `*.lotse-backup-<time>` next to each changed file, and Marshal's own folder `~/.lotse` (token, Muse plugin bundle).
- **The files** (with the environment variables the tools read themselves):
  - Claude Code: `~/.claude/settings.json` (or `$CLAUDE_CONFIG_DIR/settings.json`). The same hooks as in project mode; the Marshal status line only if there is no `statusLine` yet.
  - Muse: **no settings file.** According to the Muse docs, a faulty user `settings.json` makes the settings check fail (so every Muse session), and Muse has no offline check for a `hooks` block in it. Marshal therefore installs a user plugin `lotse` that holds only hooks (one hook capability per event, PascalCase). The bundle lives in Marshal's own folder `~/.lotse/muse-plugin`. Before installing, Muse itself checks a temp copy offline (`muse-bin-<version>.exe plugins validate`, called directly, not `muse.cmd`, no session); only then follows `plugins install --scope user` (for a newer Marshal version `plugins update lotse`). If Muse refuses the bundle, `muse-bin-*.exe` is missing (`LOTSE_MUSE_BIN` overrides the location) or a foreign plugin `lotse` already exists, Muse is skipped: "Muse: no valid global hook location found. Please connect Muse per project (lotse connect --project … --tool muse)", also in the banner. Entries that an earlier version wrote into `~/.config/muse/settings.json` are removed there again by `disconnect --all`.
  - Codex CLI: `~/.codex/hooks.json` (or `$CODEX_HOME/hooks.json`).
  - Gemini CLI: `~/.gemini/settings.json` (or `$GEMINI_CLI_HOME/.gemini/settings.json`), key `hooks`.
  - OpenCode: no settings file; the plugin file `~/.config/opencode/plugins/marshal/index.js` (or under `$XDG_CONFIG_HOME/opencode`). Found when `~/.config/opencode` (or `$XDG_CONFIG_HOME/opencode`) exists. The listing shows the file and a hash of its text.
- **What is changed.** Marshal adds only its own entries, after the existing ones. All other keys and hooks stay, including foreign hooks in the same events. Ownership is exact: `disconnect --all` removes only entries that are exactly equal to Marshal's (same command with the path of this `dist/cli.js`, same time limit). A file with broken JSON, a wrong `hooks` shape or a link as the file is refused; then the command writes nothing at all, not even to the other files.
- **Links.** If one of the files is a link (also a dangling one), Marshal does not write through it but refuses. New files are created exclusively.
- **Not atomic.** The hook commands call node with an absolute path (`"<node.exe>" "<dist/cli.js>" hook …`), because the PATH of a hook environment can be cut down (Muse clears the environment to a list). Older entries with `node "<dist/cli.js>"` still count as Marshal's own when removing, and are replaced at the next install. The files are overwritten directly, not renamed from a temp file. Claude Code reloads `settings.json` on changes and could read a half-written file in that short moment; then just restart the session or open `/hooks`.
- **Backups.** Before every change to an existing file, Marshal puts a byte copy next to it: `<file>.lotse-backup-<time>`. The backups stay; Marshal never deletes them. If nothing else about the file changed since switching on, `disconnect --all` restores exactly the original bytes; otherwise it writes the rest newly formatted (the file's line ending and BOM stay). A file that Marshal created itself is deleted again. `disconnect` removes Claude's Marshal status line only if the newest backup had no `statusLine`. If entries remain afterwards that look like Marshal's but do not belong exactly to this CLI (moved repo, other time limit), it prints a note with the file.
- **Running sessions** do not see new user hooks at once. After switching on, Marshal prints per tool what is needed:
  - Claude Code: restart the session, or check once with `/hooks`.
  - Muse: run `muse plugins approve lotse` once. Until then the Marshal hooks show `review_needed` and do not run. Then start new sessions.
  - Codex CLI: open `/hooks` once and approve the Marshal hooks.
  - Gemini CLI: work in a trusted folder. For Gemini, Marshal can only deny.
  - OpenCode: it loads plugins only when it starts, so restart OpenCode.
- **Warning for Muse.** While the Marshal plugin is installed and approved in Muse and the bridge is not running, Muse denies every approval (see "Other agents": without a headset decision it is denied). If the bridge was not started at all (connection refused), the denial says so: "Marshal is not running, so this is denied. The user decides how to go on.". Claude, Codex and Gemini show their normal prompt without a bridge.
- **Remaining risk with Muse.** If `dist/` is missing or broken (for example after `git clean` or in the middle of `npm run build`), the hook cannot start at all and gives an empty output. Muse probably treats an empty output as allow. So: do not rebuild the bridge while Muse hooks are installed, or run `disconnect --all --tool muse` first.
- **Open risk with Muse: when does Muse abort a hook?** Plugin hooks cannot set a time limit, and how long Muse lets a hook run is unknown and cannot be measured headless (in `muse exec` the hooks for read tools do not fire). Until a live test says more: the Muse shim waits at most 20 s for the headset (`LOTSE_MUSE_PERM_WAIT_MS` changes that), and the bridge holds a Muse request at most 18 s (all others 90 s). So the headset's answer or the bridge's "no decision" always comes before the shim gives up. If Muse aborts the hook earlier, it is unclear what Muse does then.
  - **Live probe (once, by hand):** a test plugin with a single hook on `PermissionRequest`, whose command writes the start time to a file, sleeps 120 s and then writes the end time (for example `["<node>", "-e", "const f=require('fs');f.appendFileSync('C:/temp/muse-hook.log','start '+Date.now()+'\\n');setTimeout(()=>{f.appendFileSync('C:/temp/muse-hook.log','end '+Date.now()+'\\n')},120000)"]`). `muse plugins install <folder> --scope user`, then `muse plugins approve <id>`, trigger a command that needs approval in an interactive Muse session, and wait. If the `end` line is missing, the gap between `start` and the abort (or the end of the Muse prompt) shows Muse's deadline. Afterwards `muse plugins remove <id>`. Adjust the 20 s/18 s with the result.
- **Duplicate hooks.** If you also installed project hooks, remove them with `uninstall-hooks`, so that events do not arrive twice.

### Live view (feed)

The Quest can follow what up to two agents write and do (`feed_subscribe`, see `src/protocol.ts`). For this the bridge reads the tool's local session log: Claude, Codex and Gemini through the `transcript_path` from their hooks, Muse through the session ID in `~/.local/share/muse/sessions/`. It reads only inside the tools' log folders, only `.jsonl`, once per second and only the newly appended bytes (at most 64 KB per read). A line that is not complete yet is buffered across several reads up to 1 MB (Gemini writes its whole message list into one line; only new messages come from it); longer lines are skipped. More than 30 new entries at once go out in several messages. Unknown formats give no entries, never a crash. For Claude the Agent SDK is not used: it reads whole sessions, not just what was appended. Single lines over 1 MB (with Gemini, which writes its whole message list into one line, this can happen in long sessions) are skipped; then entries are missing there. Because at most 64 KB are read per second, the feed can lag a few seconds behind on large logs.

- **Privacy.** Each entry is at most 400 characters, secrets are blacked out with `redactSecrets` and absolute paths are shortened. The feed is display only: it never changes risk, gestures or decisions, is never recorded, never logged and stored nowhere, and no AI is asked for it. Like everything else it goes unencrypted (`ws://`) over the LAN to the paired Quest; shortening and redaction limit what is visible on the way. The subscriptions end when the Quest disconnects.

## Agents: title and project

Instead of just "Agent 1", the Quest shows what an agent is working on (`agent.title`, at most 40 characters) and in which project (`agent.project`, the last part of the working folder, at most 30 characters).

- **Title by rules.** On the first `UserPromptSubmit` of a session: the first sentence of the first line of the prompt, blacked out with `redactSecrets`, absolute paths shortened (`~/…`, `…/file`), one line without invisible characters, at most 40 characters.
- **Title from the AI (optional).** If the explanation AI is on, the bridge then asks haiku once per session for a title of at most 6 words and, if it is usable, sends a new `agent` message. The prompt goes into the call only redacted, with shortened paths, cut to 2000 characters and fenced as untrusted data. The answer is cut to one line, 6 words and 40 characters and redacted once more. Errors or unusable answers leave the rule title in place.
- **The prompt itself stays on the PC and is stored nowhere.** It is not copied into the event, not recorded and not logged; the recording (`--record`) gets only the title, anonymised like every text and cut to 40 characters.

## Agents: plan

The Quest can show each agent's task list: what is done, what is running, what is open (`agent.plan`, contract `.superpowers/sdd/2026-11-12-contract-agent-plan.md`). The plan comes only from the agents' own plan tools; the bridge never invents steps.

- **Claude Code.** `TodoWrite` (the whole list on every call) from `PreToolUse` and `PostToolUse`; plus the newer `TaskCreate`, `TaskUpdate` and `TaskList`, which count only after the run (`PostToolUse`, the id is in the result). The shapes come from `sdk-tools.d.ts` of `@anthropic-ai/claude-code` 2.1.191; whether `tool_response` in the hook is exactly this object is not checked live (see report `task-p1-report.md`). Unknown shapes change nothing.
- **Codex.** `update_plan` from the hooks, if Codex fires them for it (not confirmed), and also from the rollout log (`~/.codex/sessions/…`, the hooks' `transcript_path`): on the first read the last 1 MB, then once per second only what was appended (at most 256 KB per read), only lines with `update_plan`, at most 16 sessions.
- **Gemini CLI.** `write_todos` from `BeforeTool`/`AfterTool`. `cancelled` and `blocked` become `pending`, like any unknown status.
- **Muse.** No known plan tool. If Muse reports a tool with one of the names above in the same shape, it counts; otherwise a Muse agent has no plan.
- **Subagents.** Claude subagents report their tools under the main agent's `session_id`. Plan calls from a payload with a non-empty `agent_id` are ignored, so that a subagent does not replace the main agent's plan. The field name comes from the Claude Code hook docs and is not checked live. If a session never showed an `agent_id`, the fallback is: between `SubagentStart` and `SubagentStop` (or until the next prompt, `Stop`, session start or end) plan calls are ignored.
- **Late and idle sessions.** A hook that arrives after `SessionEnd` brings back no plan and no Codex log watching (only a new `SessionStart` of the same session does). After 30 minutes without any event of a session, its plan state, its rate limit and the watching of its Codex log are dropped (the last plan sent stays on the agent). When the bridge shuts down, an `/ev` still running starts no plan timer and no watching any more.
- **Known limit with Codex.** If `update_plan` calls come both from the hooks and from the log, the plan can switch between two states for up to 1 s until the log has caught up.
- **Without a plan tool** `plan` is missing entirely (never an empty list); the Quest then shows only the latest actions.
- **Limits.** At most 12 steps (`more` counts the cut ones), each step at most 80 characters, blacked out with `redactSecrets`, absolute paths shortened, one line without control and invisible characters (those are removed first, so that they cannot prevent a path from being shortened). A list is cut after 200 entries; with a longer list `more` is therefore a lower bound. Only the first 12 usable entries are redacted and shortened, the rest only counted. A plan change sends an `agent` message, at most one per agent every 500 ms; the latest state always goes out. A plan whose steps are all done stays until the session ends or a new one replaces it; on `SessionEnd` it goes away. Broken input is skipped.
- **Recording and demo pack.** A plan change is a `plan` event; the recording (`--record`) anonymises the steps like other text, and the demo pack's check for forbidden strings covers them. `demo/jury.ndjson` gives all four demo agents plans that change with their actions.

## Replies from the headset (Claude Code only)

On the Quest you can reply to an agent that is done or waiting (Quest keyboard or dictation). Claude gets the reply as a system reminder and keeps working.

- **The hook.** For Claude the `Stop` hook is `node "<dist/cli.js>" hook --source claude --event Stop --listen` with `"async": true`, `"asyncRewake": true` and `"timeout": 900`. The docs allow either of the two background switches; with both the session never blocks, whichever one a Claude Code version requires. From the Claude Code docs (hooks): `asyncRewake` "runs in the background and wakes Claude on exit code 2. The hook's stderr, or stdout if stderr is empty, is shown to Claude as a system reminder"; and "Claude Code still enforces `timeout` on a hook you run with `asyncRewake`". So the hook never blocks the session.
- **Flow.** The hook reports the Stop event as before and then waits through `GET /reply?sid=<sid>&cwd=<cwd>` (or `&transcript=<file name>`; token, host and origin checks as for the other endpoints) up to 880 s for a reply, so before the 900 s time limit (`LOTSE_LISTEN_MS` can only shorten that, for tests).
- **Who may wait.** Without an ingest token the bridge refuses `/reply` entirely (403; the CLI always sets one). Only a session that ran in the last 2 h may wait (SessionStart, prompt, notification, Stop or a tool event; otherwise 404; so the Stop the hook reports itself just before is enough), and only with the working folder or transcript name its own hooks reported (otherwise 409). If a hook of this session is already waiting with a different folder, it stays and the new one gets 409. At most 32 hooks wait at once (otherwise 429).
- **Trust boundary.** Whoever has the ingest token (`~/.lotse/token` or `LOTSE_TOKEN`) is inside the trust boundary: they can report events and so also wait as a hook. The checks above prevent mix-ups and hijacking between sessions, but do not replace a secret token. When a reply comes, the hook writes `Message from the user via the Marshal headset: <text>` to stderr and exits with code 2; Claude wakes up with it. Without a reply, on errors, a wrong token or a bridge that is off, it ends silently with 0.
- **The bridge.** `agent_reply {sid, text}` is accepted only from the paired socket, at most one delivered reply per agent every 5 s (otherwise `error` `rate-limited`; undelivered ones do not count). The text: line breaks stay, other control characters are dropped, at most 1000 characters, not empty. It is delivered only to a waiting Claude hook of an agent that is done or waiting (or whose hook is waiting right now). The answer `agent_reply_ack {sid, delivered}` says whether that worked: `true` only once the reply has been written to the hook without error; for Muse, Codex and Gemini `delivered` is always `false`. At most one hook waits per agent; a new one replaces the old one (the old one gets `{}`), as do `SessionEnd`, 15 min passing and the bridge shutting down.
- **Privacy.** The text is handed only to the waiting hook. It is never logged, never recorded and stored nowhere; for a delivered reply the recording gets only a `reply` event without text, and the agent shows "Reply sent". Undelivered replies leave no trace. The reply is always the user's own input, never from the AI.
- **Older installs** still have the old `Stop` hook: reinstall (`lotse connect --project <dir>`).

## Agent details

The Quest can ask for details about an agent: `{ "type": "agent_detail_request", "sid": "…" }`, only from the paired socket, at most once per agent every 3 s (otherwise `error` `rate-limited`; an unknown agent gives `unknown-agent`). The answer is `{ "type": "agent_detail", sid, title, summary, recent, waitingFor, source }`.

- **recent:** the session's latest tool starts as rule texts, newest first, at most 5 of at most 80 characters each: "Reads src/cart.ts", "Edits src/cart.ts", "Searches the project", "Runs tests", "Runs: <command, redacted, paths shortened, 40 characters>", "Uses WebFetch". The bridge keeps only these texts, not the tool inputs.
- **waitingFor:** the explanation of this agent's open approval request; otherwise, for a waiting agent, the text for the last notification ("Waiting for your next instruction.") or "Waiting for approval in the terminal: <tool>"; otherwise `null`. At most 140 characters.
- **summary (rules):** from the state and `recent`, for example "Edits src/cart.ts. Before that: Reads src/price.ts. Changed files: src/cart.ts.", at most 280 characters. This always comes at once, with `source: "rules"`.
- **summary (AI, optional):** If the explanation AI is on and there is a readable transcript, a second `agent_detail` with `source: "ai"` follows; the Quest shows the newest. For it, haiku summarises the last 30 entries of the local transcript: Claude, Codex and Gemini name the path in the hook (`transcript_path`), for Muse the bridge looks for `~/.local/share/muse/sessions/YYYY/MM/DD/<sid>/session.jsonl` of the last 3 days. Only a `.jsonl` file is read whose real path (links resolved) lies in the transcript folder of that tool (`~/.claude/projects` or `$CLAUDE_CONFIG_DIR/projects`, `~/.codex/sessions` or `$CODEX_HOME/sessions`, `~/.gemini/tmp` or `$GEMINI_CLI_HOME/.gemini/tmp`, the Muse folder), and of it only the last 64 KB. From each entry at most about 300 characters of text are taken (without ids, timestamps and thinking blocks), then redacted, paths shortened and fenced as untrusted data. The answer is cut to one line and 280 characters and redacted once more. It is kept in memory per agent for 30 s, never stored, recorded or logged. On errors the rule summary stays, and the AI is not asked again for this agent for 30 s.
- **Memory.** What the bridge keeps per session for details and titles (labels, notification, transcript path, summary, rate limit) is forgotten on `SessionEnd`, and after 2 h without an event; at most 200 sessions, the one silent longest drops out first.
- All of this is display text: it changes neither risk nor gesture nor decision.

## Explanation AI

Every approval request comes with an explanation in plain words and 2 to 3 suggested replies.

- **Rules first.** `perm_open` always carries `explain: { text, replies, source: "rules" }`, from fixed texts per risk reason. This works without AI and without a network.
- **AI afterwards (optional).** If the explanation AI is on, the bridge later sends `perm_explain { id, explain }` with `source: "ai"`. The client replaces its explanation with it.
  - For a safe request (`safe`) the AI text replaces the rule text.
  - For every other request (destructive, network) `text` stays the rule text. The AI's sentence is carried in the extra field `aiText`; the client shows it below the rule text, labelled as AI. The suggested replies come from the AI.
  - For a cut command (`request.truncated`) the AI is not asked at all: the rule text stays, without `perm_explain`.
  - `perm_explain` comes only while the request is still open: after a decision, a timeout or a cancellation nothing more comes for this id.
- **What it does.** It writes display text in English (explanation at most 140 characters, replies at most 70, at most 3 replies, without control, bidi and zero-width characters). The command goes into the prompt only redacted (`redactSecrets`), with shortened absolute paths and in a `<command>` block. Outside the block stand the classifier's risk reason (`Reason (trusted): …`) and whether the command is cut; the AI is asked to name this reason. At most 2 `claude` processes run at once, each is ended after 25 s. The JSON keys the AI answers with (`erklaerung`, `antworten`) are internal and unchanged.
- **What it does not do.** It decides nothing and changes neither risk class nor gesture nor the 90 s wait. An `allow` is always checked the same way, whatever a text says (destructive: two hands). If the AI plays down the risk of a request that is not safe (destructive or network) ("harmless", "not dangerous", "nothing to worry about", "can be restored", "only old files", "safe" and similar, in English or German), `aiText` is dropped; reassuring suggested replies are replaced by the rule replies. If nothing of the AI is left, no `perm_explain` comes. The client may send the suggested replies back only as the `message` of a `deny`, never as an `allow`.
- **Requirement.** The AI runs through `claude -p` (Claude Code CLI, installed and signed in), with `--model haiku --tools "" --setting-sources ""`, an empty working folder and no project hooks, so without feedback into Marshal. If `claude` is missing, not signed in or fails to start, the rule explanation stays and a log line appears. After 3 failures in a row (error or time limit) the explanation AI switches itself off for the rest of the process and reports this once with `Explanation AI switched off: …`. Agent titles and summaries have their own such switch: if they fail, the explanations of approvals stay on, and the other way round. Only `claude`'s exit code is logged, never its error output (it can contain parts of the prompt); errors with titles and summaries are not logged one by one at all. When all requests a running `claude` process should answer are closed, it is aborted (checked every 500 ms); its place among the 2 concurrent ones becomes free only once the process has really ended.
- **Switching on and off.** `--explain cli|off` with `start` and `demo`. The default is `cli` when an executable `claude` is on PATH (only looked for, not started; only in absolute PATH entries, `.` and other relative entries are skipped; on Windows only `claude.exe`, on Linux/macOS with execute permission), otherwise `off`. An explicit `--explain cli` without a `claude` found is a usage error (exit 2). After the start it says `Explanation AI: on (claude -p, haiku)` or `Explanation AI: off`. With `--explain off` there is not a single AI call. The same holds in demo mode. On exit, running `claude` processes are aborted.
- **Privacy note.** With `cli`, per request this goes to the Claude API: the tool name, the risk class and its reason, whether the command is cut, and the command (otherwise URL or path), at most 4000 characters. Secrets are blacked out with `redactSecrets`. Absolute paths are shortened: the home directory becomes `~`, other user folders `~other`, the user name `<user>`, and every other absolute path keeps only its last part (`…/plan.md`). Relative paths and URLs stay as they are. The prompt goes to `claude` as a command-line argument: on Linux and macOS it is therefore visible with `ps` while the call runs, also to other users of the machine. If you do not want that, start with `--explain off`. The same AI supplies the agent titles and summaries: for those, the first prompt of each session (at most 2000 characters) and, on a detail request from the Quest, the last 30 transcript entries also go to the Claude API, both redacted and with shortened paths (see "Agents: title and project" and "Agent details"). With `--explain off` none of this leaves the PC.

## Effects of a request (impact)

Next to a destructive request the Quest shows facts about what it would hit (`perm_impact`, contract `.superpowers/sdd/2026-11-12-contract-impact-halt.md`, code `src/impact.ts`). The bridge finds them without AI, without running anything from the request, without starting a process and **without reading a file**: only `lstat` and directory listings. If no `perm_impact` comes, the Quest shows "Effects unknown". An impact never changes risk class or gesture.

- **Principle.** Marshal names only losses that are certain. It never says something is safe or recoverable. `recoverable` is therefore only `no` (certain loss) or `unknown`; there is no `yes` or `partly` (not in the demo pack either, a build check prevents it). In doubt it says "Effects unknown". No warning is not a statement.
- **Only a simple command.** Facts come only when the **whole** command line is exactly one simple command the bridge understands, with literal arguments. Otherwise it is always `{kind: "other", recoverable: "unknown", reason: "Several steps or unclear. Effects unknown."}`, without target, without numbers and without a single disk access. Otherwise the effect of one part would appear as the effect of the whole request (a script that changes directory first, a redefined `rm`, a second command on the same line).
  - Bash: no `;`, `&&`, `||`, `|`, `&`, line break, no redirection, no here-document or here-string, no subshell or brace group, no `` ` `` or `$(…)`, no process substitution, no function, no keyword (`if`, `for`, `while`, `case`, `!`, `time`), no variable assignment in front, no expansion (variables, `~` at the start of a word, globs, brace expansion, `$'…'`), no backslash, no `#`. The command word stands plainly (without quotes, without a path) and is not `command`, `builtin`, `exec`, `eval`, `source`, `.`, `sudo`, `env`, `nohup`, `xargs`, `find`, `sh -c` or similar. A `cd` in front makes the line unsuitable.
  - PowerShell: one command, no `;`, `|`, `&`, `&&`, `||`, line break, `$(…)`, script block, no variable, no splatting, no call operator, no `iex`/`Invoke-Expression`, no .NET call (`[…]::…`), no redirection. `[ ] * ?` in a path are wildcards for PowerShell, also in quotes: only through `-LiteralPath` is such a path literal.
  - Commands and switches understood: `rm` with `-r -R -f -v -d -i -I --recursive --force --verbose --dir --` (a target `.` or `..` makes the line unsuitable), `rmdir` (`-v`), `unlink`; `Remove-Item` and `rm`, `del`, `rd`, `ri`, `erase`, `rmdir` in PowerShell with `-Recurse`, `-Force`, `-Path`, `-LiteralPath`, `-Confirm:$false`, `-ErrorAction …`; `git push` with `--force`/`--force-with-lease`/`-f`/`+refspec` (at most remote and refspec), `git reset --hard [commit]`, `git clean -f[dxXq]` (without `git` options in front). Any other switch makes the line unsuitable. `Write`/`Edit`/`MultiEdit`/`NotebookEdit` (and Gemini's `write_file`/`replace`) check their path field.
  - A line over 4,096 characters is unsuitable without being parsed. More than 32 targets: unknown.
  - If the command comes as a list of arguments (`["rm","-rf","a b"]`), it is never joined into a line: the elements are the literal words of one command (`a b` is one path). If a shell stands in front, only the form `bash -c|-lc "<line>"` (likewise `sh`, `zsh`, `dash`, `pwsh -Command`, `powershell -NoProfile -Command`) is read, with that shell's rules; any other form, an empty list, more than 64 elements or an element that is not text: unsuitable.
  - Other agents on Windows: the line must be suitable in both the bash and the PowerShell reading and give the same result, otherwise unsuitable (`rm -rf x` is not a valid call in PowerShell).
- **Result.** `reason` is always one of eight fixed sentences; nothing from the request or the file system goes into it:
  - Target not in a Git project (no `.git` in the target's folder or above): `no`, "Not in a Git project: gone for good." Plus the number of files and bytes and whether the target lies outside the working folder (`outsideProject` is missing when the working folder is the home directory or a root: there "in the project" would mean nothing).
  - A target folder that itself contains a `.git` entry: `no`, "Deletes a whole Git project with its history: gone for good."
  - Target in a Git project: `unknown`, "In a Git project. Marshal does not check whether everything is saved." With the same numbers. The bridge does not check whether something is committed: the agent can write everything under `.git`.
  - `git reset --hard`: `no`, "Discards all unsaved changes in the project. They are gone afterwards." `git clean -f`: `no`, "Deletes every file that is not in Git. They are gone afterwards." Forced push: `no`, "Overwrites what is on the server. Anything new there is gone afterwards." For these three nothing on disk is looked at; there is no `commitsLost`.
  - A suitable command whose target is unclear: `unknown`, "Target unclear. Effects unknown.", without target and numbers. These are: a target that does not exist; a link (symbolic link, junction) anywhere in the path, also as the last part; a `/` or `\` at the end when the last part is not a real folder; a network or device path; several targets of which one is unclear; a working folder with a link in it. The same sentence comes when the global check budget is used up.
  - Unsuitable lines: see above, "Several steps or unclear. Effects unknown."
  - As `target` goes the path the bridge actually checked, resolved and shortened (for example `~/code/legacy-site`), never a file name from inside.
- **Working folder.** The numbers describe the path as the bridge resolves it from the request's working folder (`cwd`). If the agent's shell works in another folder (say after a `cd` in an earlier call), the command acts elsewhere. That is why the Quest shows the checked path: if it does not match the command, the command counts.
- **How the path is read.** The working folder (it comes from the payload and is as untrusted as the request) and every target are walked from their root part by part with `lstat`, as written: `..` is not shortened away beforehand, but only taken after the part before it was checked as a real folder. At the first link, missing part or non-folder the check stops, without touching anything behind it.
  - Windows: a path like `/c/Users/x` (Git Bash) counts as `C:\Users\x` only if `<drive of the working folder>:\c` does not exist; otherwise it is ambiguous. Every other path starting with `/` or `\` (`/tmp`, `/cygdrive/…`, `/mnt/c/…`, `//…`) is unknown, because MSYS mounts are not known without running something. Names with a dot or space at the end, data streams (`:`) and reserved names are unknown.
- **Git.** The only question: is there a `.git` entry (folder, file or link) in the target's folder or above (at most 40 levels)? Answered with `lstat`; none of it is read.
- **Limits of the check.** At most 20,000 entries and 400 ms for the whole check of one request (paths, Git question, counting); after that `filesCapped: true` and `files` is a lower bound. A link in the tree counts as one file and is never followed. Directories are read in small pieces (never more names than the remaining budget). The check yields the event loop every 32 file-system calls and between two checks; parsing a line of up to 4,096 characters takes a few milliseconds. Globally: at most one check in the whole bridge at a time, up to 8 waiting (older ones are dropped), at most 2 s of check work per 10 s; beyond that `unknown` without disk access. If a check hangs longer than 2 s (say on an `lstat` on a hanging share), it frees its place. `perm_impact` goes out only while the request is open; the `snapshot` has `impacts`. In demo mode (`inject`) nothing is checked.
- **Threat model.** The coding agent controls the working folder (including `.git`), every text of the request and the working folder in the payload, and it knows the ingest token. The check may run nothing, open no connection and tell the human nothing reassuring that it cannot know.
- **Network.** Before every `lstat` the path must be a local absolute path: no UNC (`\\host\share`, `//host/share`), no device path (`\\?\`, `\\.\`), no drive-relative path (`C:foo`), no control characters. On macOS `/net`, `/Network`, `/Volumes`, `/home` (automount) and the same under `/System/Volumes/Data` are refused (regardless of case), on Linux `/net`, `/mnt`, `/media` and `/run/user/*/gvfs`. This also holds for paths that lead there through `..`, and for the working folder.
- **No process.** `src/impact.ts` imports, neither directly nor through other modules, anything that can open a process, worker or socket, and none of these modules names `fetch`, `WebSocket` or `process.binding`; a test walks the import graph. A second test shows that the check uses only `lstat` and `opendir` from the file system.
- **Remaining risks.**
  - A drive letter mapped to a network share (`Z:`, also `subst`) looks like a local path: `lstat` on it reaches the share the user connected themselves. A single `lstat` on a hanging share can take longer than 400 ms.
  - The check works with names (Node has no `openat`/`fstatat`). A process that swaps entries for links during the check can make it touch a path behind a link before it notices and stops with `unknown` (each folder's identity is checked right after listing, and a child that the listing did not report as a link ends the check). This needs an agent that can already run code; it gains nothing from it, because the check only supplies numbers and no reassuring verdict is left.
  - Windows reparse points other than links and junctions (such as OneDrive placeholders) are reported by `lstat` as ordinary folders; listing them can make the sync provider download them.
  - The impact is a snapshot taken when the request opens; the agent can change the target before the human decides.

## Halt all

A gesture in the headset stops all agents before their next step (contract `.superpowers/sdd/2026-11-12-contract-impact-halt.md`, code `src/halt.ts`, `src/server.ts`).

- **Halting.** The paired Quest sends `{type:"halt", on:true}` (from a socket that is not paired: `error not-paired`). The bridge answers everyone with `halt_state {on, since, enforcement}`; the same state is in the `snapshot` as `halt`.
- **While halted:**
  - every open approval is denied with "The user has halted all agents. Run nothing further and wait for their instruction." (`perm_closed` with reason `halt`); a later decision for it is refused;
  - every new approval gets the same denial at once, without `perm_open`, with or without a connected Quest, also a broken request (never "no decision");
  - every pre-tool hook (`PreToolUse`, Gemini's `BeforeTool`, OpenCode's `tool.execute.before` through the plugin) gets a denial with the same message: `/ev` answers in Claude Code's PreToolUse format (`permissionDecision: "deny"`), the shim prints it in the tool's format (Gemini: `{"decision":"deny","reason":…}`). The hook also sends the header `X-Lotse-Hook: PreToolUse` (the shim, and with the `http` transport the installed `PreToolUse` hook); the bridge then denies from the headers alone, before reading the body, as with `/perm`. Without this header, a body that is too large (over 1 MB) or broken still gets the denial instead of 413/400;
  - agent status, plans and feeds keep running.
- **Not halted** nothing changes: every hook output and every wait is exactly as before (`test/fixtures/hook-output-baseline.json` was captured before this change and is compared; only the product name and the English wording of the Muse denials were updated since). A pre-tool hook stays bound to its 500 ms from process start.
- **Slow bridge or slow hook (halt marker).** While halted, the bridge keeps the file `~/.lotse/halt` with its process ID and start time; on release and on a clean exit it is deleted, on halting it is overwritten (never through a link). A bridge that is not halted removes any marker that exists anyway: at start and whenever it answers a hook.
  - Pre-tool and approval hooks are installed with `--event`, so the hook knows what it is before stdin. For these two, **every** path on which the hook would end without a decision goes through the marker: stdin comes too late, empty or cut, its own budget is used up before sending, the bridge does not answer in time, it answers without a valid 200 response, or an error occurs. If the marker exists and the process in it is running, the hook prints the same denial as the bridge.
  - If the bridge answers, its answer counts, also against a marker. On a refused connection (bridge off, also crashed) the marker is ignored, so a crash never blocks an agent. Hooks installed before this change without `--event` recognise their kind from the (also cut) stdin; with a completely empty stdin they cannot. Running `lotse connect` again fixes that.
  - The marker is read only if it and `~/.lotse` are not links.
- **What each source obeys** (`enforcement`, only sources with running sessions):
  - Claude Code `every-step`: `PreToolUse` is installed for every tool and can deny.
  - Gemini CLI `every-step`: `BeforeTool` runs before every tool, before Gemini's own check, and can deny.
  - Codex CLI `every-step`: `PreToolUse` with a documented denial for shell, `apply_patch` and MCP tools, so everything that changes something; whether `update_plan` and web search reach the hook is not confirmed.
  - OpenCode `every-step`: Marshal's plugin asks the hook in `tool.execute.before`, which runs before every tool call, and throws on the denial.
  - Muse `requests-only`: `PreToolUse` is installed and gets the same denial, but its format comes only from third-party sources and hooks for read tools did not fire there; only the approvals are certain.
  - None of this is checked live with the tools.
- **Continue.** Only three ways:
  1. `{type:"halt", on:false}` from the paired Quest;
  2. the bridge console: while halted and only when stdin is a terminal (TTY), the line `continue` (or the older `weiter`) and Enter releases; otherwise nothing typed there has any effect on the halt, and anything typed before the halt does not count. This keeps out an agent that can only write files or ask for tools. One that can run code as the same user can inject console input (Windows `AttachConsole`/`WriteConsoleInput`, Linux `TIOCSTI` where allowed, or a PTY in which it started the bridge itself);
  3. restarting the bridge (the halt lives only in memory).
  There is **no** HTTP way: all agents know the ingest token (it is in their hook configuration), so a halted agent could otherwise release itself.
- **Console.** On halting and, while no Quest is connected, every 60 s: "Halted. To go on: press Continue in the headset, or type continue here and press Enter." (without a TTY: "Halted. To go on: press Continue in the headset, or restart the bridge."). On release: "Marshal: halt released (headset)" or "(console)". A halt survives the Quest disconnecting.
- **What halt is and what it is not.** Halt is a brake, not a sandbox. It is enforced by the agent's program, which asks the hook before every tool and obeys its denial; the model inside has no control over that. But:
  - An agent that can run commands can end the bridge, and then the halt is released (a restart releases it). A source with `requests-only` or `none` can keep running everything it needs no approval for during the halt.
  - An agent that can write files can delete the halt marker or create one. The marker closes the gap of a slow bridge or a slow hook for cooperative agents and is no lock against a hostile one; a running bridge that is not halted removes a created one.
  - An agent that can write into the Marshal folder can change the code its hooks run. That defeats every approval, not just the halt. **So install Marshal outside every folder an agent works in**, and do not let an agent work unattended in the Marshal folder itself while Marshal is active.
  - If the bridge is not running at all, nothing changes compared with today (the agents ask in their own dialogs).
  - Processes an agent started in the background before the halt keep running; the halt stops only the agents' next step.
  - Whether a pre-tool hook runs at all is set in the hook configuration, which the agent can write in the project (`.claude/settings.json`, `.gemini/settings.json`); a change takes effect from the next session.
- **Demo pack.** The Quest's player halts locally; the pack needs no halt messages.

## Demo pack

`lotse pack` turns an anonymised recording into a pack that the Quest app plays without a PC: the bridge's message stream with timestamps and, per approval request, what happens after Allow or Deny.

- **Command.** `node dist/cli.js pack ../demo/jury.ndjson -o ../demo/jury.pack.json --overrides ../demo/jury.overrides.json`. `-o` and `--out` are the same. `--explain` is `off` by default here, so that the pack is reproducible; with `--explain cli`, `pack` asks the explanation AI for each request in turn (25 s time limit per call) and shows `Explanation n/N`. The committed `demo/jury.pack.json` is built with `off`; a test checks that it equals a fresh build.
- **Format.** `{ version: 1, budgetUsd, durationMs, messages: [{ t, msg }], perms: { "<id>": { onAllow, onDeny } }, agents?: { "<sid>": { title, summary, recent, waitingFor } }, replies?: { "<sid>": "…" } }`. `messages` starts with an empty `snapshot` at `t = 0` and then holds exactly the `agent`, `incident` and `perm_open` messages the bridge would send live, sorted by `t`, with two exceptions (see **Wait time of the recording**). A test compares this with a real `startServer`.
- **Requests.** The ids are `p1`, `p2`, … in recording order, `createdAt` is `t`, `expiresAt` is `t + 90000`. The risk comes from the same classifier with the same `<repo>`/`<abs>` mapping as `demo`. `request.command` is blacked out with `redactSecrets`. Like `path` and `paths`, it deliberately keeps the placeholder `<repo>/`, so that no local path is in the pack; the player removes `<repo>/` for display. The explanation text already shows the path relative to the project. A `perm_closed` is not in the pack: the player creates it itself when a decision is made or the 90 s run out.
- **Consequences (player contract).** `onAllow` and `onDeny` are each a patch `{ sid, status, lastAction }`, by default `status: "working"` with `Allowed: <tool> <target>` or `Denied: …`. The player
  1. takes only `status` and `lastAction` into its current state of agent `sid`,
  2. sets its `since` to the time of the decision,
  3. adds `decision time - request.createdAt` to its own sum of juror wait times for `sid`,
  4. and then plays the timeline on.

  Shown wait time of an agent = `waitingMsTotal` from its last `agent` message in the pack + the sum of juror wait times for its `sid`.
- **Wait time of the recording.** The recording itself waited for an approval; the pack does not replay that, so that no old state comes back after the juror's decision.
  - From a `perm_open` until the next `tool_start`, `tool_end`, `stop`, `prompt` or the next approval request of the same agent, its `agent` messages that still show it `blocked` or with "Waiting for approval" are left out.
  - `waitingMsTotal` in the `agent` messages does not include the recorded approval wait times (the time `blocked`); other wait times ("Waiting for input") stay in.
- **Check before writing.** If the pack contains `C:\`, `C:/`, `/Users/`, `/home/`, `sk-` or `ghp_` anywhere, `pack` stops with an error that names the place, and writes nothing.
- **Overrides.** A JSON file keyed by id: `{ "p11": { "onAllow": "…", "onDeny": "…", "explain": { "text": "…", "replies": ["…"] } } }`, every field optional. `onAllow`/`onDeny` replace `lastAction` (at most 80 characters), `explain` replaces the explanation (`source: "manual"`, at most 140 characters, 1 to 3 replies of at most 70). Unknown fields, ids that are not in the pack, texts that are too long, and control, bidi and zero-width characters are an error naming the file and field. `demo/jury.overrides.json` covers the two destructive requests of the jury demo (`p11` `rm -rf ../legacy-site`, `p14` `git push --force origin main`). The optional field `impact` (shape like `perm_impact`, `recoverable` only `no` or `unknown`, target and reason each one line of up to 120 characters, numbers whole and not negative) goes into the pack as `perm_impact` right after the `perm_open` of this request; the jury demo has it for `p11` (214 files, outside the project, "Not in a Git project: gone for good.") and `p14` (forced push, the fixed sentence).
- **Agent details.** The `agents` key of the same file holds hand-written details per session: `{ "agents": { "demo-a1": { "title": "…", "summary": "…", "recent": ["…"], "waitingFor": "…" | null } } }`, with the limits of the live `agent_detail` message (title 40, summary 280, at most 5 `recent` of 80 each, `waitingFor` 140 characters or `null`) and the same rules for control and invisible characters. They land unchanged in the pack under `agents`; the player answers `agent_detail_request` from them, offline (`source: "rules"`). Every `agent` message of this session carries `agent.title` = this title. Details for a session that is not in the recording are an error; the check for forbidden strings applies to them too. `demo/jury.overrides.json` has details for `demo-a1` to `demo-a4` (cart badge, checkout totals with a forced push, moving the old pages with the deletion of `../legacy-site`, product search with price filter). The four demo agents come from four vendors: `demo-a1` Claude Code, `demo-a2` Codex (the forced push), `demo-a3` Muse (the deletion), `demo-a4` Gemini CLI; the recording names them with `source` on every event of the session. A rule explanation names the agent that asks ("Codex runs a command: …"), a Gemini card adds "Gemini (Deny only): ".
- **Replies offline.** The `replies` key holds, per session, a fixed reaction of the agent to every reply from the headset (one line, at most 80 characters), for example `"demo-a2": "Understood. I won't push to main; I'll open a pull request instead."`. The player answers `agent_reply` with `agent_reply_ack delivered: true` and shows this reaction. Sessions that are not in the recording are an error; the check for forbidden strings applies here too.

## Risk classifier: scope and known gaps

The bridge sorts every Claude Code tool call into `safe`, `network` or `destructive` (`src/risk.ts`). The headset uses the tier to set the approval cost: one pinch-and-hold for `safe` and `network`, a two-hand confirmation for `destructive`.

**The classifier is a UX layer on top of Claude Code's own permission system, not a sandbox.** It never grants anything. Claude Code still asks for every call its permission rules require, and the classifier only decides how much effort the approval takes. The classifier is deterministic code (no LLM). It reads the command text statically with a quote-aware shell lexer (`src/risk/lexer.ts`) and resolves ambiguity towards the higher tier. Any command it cannot determine statically counts as `destructive`: non-literal command words, PowerShell call operators on expressions, xargs/parallel replace strings, unknown shell options, and code fed to a shell or interpreter through stdin.

By policy, running a script file from the project (`bash build.sh`, `node x.js`, `npm run x`, `make`) stays `safe`. Its contents are not inspected.

**Display of the command.** The headset shows `request.command`, cut to 300 characters; a cut command (`truncated: true`) always needs the two-hand hold. A command string is shown as it is. A command that comes as an argument array (Codex `cmd`, MCP tools, `["bash","-lc","…"]`) is never joined by spaces, because `["rm","-rf","a b"]` deletes the single path `a b`. It is rendered by `src/argv.ts` so that every element stays one word: an element made only of ASCII letters, digits and `_ - . / : = + , @ %` is shown as it is; any other element in single quotes (`'` written as `'\''`); an element holding a control or invisible character (C0/C1 controls, bidi and zero-width format characters, line separators, any space other than U+0020) as bash ANSI-C quotes `$'…'` with that character as an escape (`\n`, `\e`, `\x01`, `\u202e`), never raw; an empty element as `''`. The command word is quoted when it contains `=` (it would read as an assignment). A backslash is quoted too (`'C:\p\x'`), since unquoted the POSIX lexer reads it as an escape. The bridge's own bash lexer reads the rendering back as exactly the elements (`$'…'` decoded as bash does), tested with 400 generated hostile arrays. The request then carries `argv: true` (optional; older headsets ignore it). Truncation and the two-hand rule apply to the rendered text. The activity feed renders arrays the same way.

**Argument arrays are classified from their elements.** Element 0 is the command word, every other element one literal argument; nothing in an element is read as quotes, separators or expansions. A shell, interpreter or wrapper in element 0 is read by the same rules as on a command line, so `["sh","-c","rm -rf ~"]` classifies `rm -rf ~` with the bash rules, `["pwsh","-Command",…]` with the PowerShell rules and `["cmd","/c",…]` with the cmd rules (with or without a path or `.exe`). For a non-Claude agent on Windows the elements are read in both dialects, as a command string is. The result is never below the old reading of the elements joined by spaces (a harness may run an array that way), so it is the worst of both. The joined reading was wrong in the dangerous direction for writer destinations with spaces (`["cp","x","../x y"]`, `["rsync","a","/etc/x y"]`, `["docker","cp","a","/etc/x y"]`: joined, the destination was `y`), for `["tar","-xf","a;b","-C","/"]`, for code in a perl option (`["perl","-m","x;system 1","x.pl"]`), for SQL across a newline (`["psql","-c","DROP -- c\nTABLE users"]`) and for many `bash -c` strings (`["bash","-c","curl … -o i.sh && bash i.sh"]`). A Codex call whose `cmd` and `command` differ as rendered (`["rm","a b"]` against `rm a b`) is unclear.

**Length cap.** A command longer than 16,384 characters (an argument array counted as rendered), any other top-level string field longer than that, a tool name longer than that, or an array with more elements than that, is not lexed at all: `destructive`, "Command too long, not checked", which brings the two-hand hold and a cut display. It is decided in constant time before any text is read (1 MB and 10 MB commands well under 10 ms; a burst of 20 such requests keeps the event loop responsive). The cap was measured on the pathological shapes of the timing tests (pipes, here-document, many targets, ReDoS shapes, each as Claude, Codex with both dialects, and as a Codex argument array): about 200 ms worst at 64 KB, 63-108 ms at 32 KB, about 30-40 ms at 16 KB.

**Statement breaks.** The lexer reads CR LF, CR, VT, FF, NEL (U+0085), U+2028 and U+2029 as a line break in every dialect; inside quotes they stay part of the word. Tested on the development machine with harmless commands: PowerShell 5.1 ends a statement at LF, CR and CR LF and reads VT, FF, NEL, U+2028, U+2029 and the Unicode blanks (NBSP, U+1680, U+2000-U+200A, U+202F, U+205F, U+3000) as blanks between words; bash, sh and dash end a statement at LF and CR LF only; `cmd /c` stops reading the line at LF. PowerShell 7 was not installed and is not tested.

**Invisible and control characters.** A command (string, array element, Codex `cmd`) holding a control character other than `\n` and `\t`, a bidi control (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069), a zero-width or invisible format character (U+200B-U+200D, U+2060, U+FEFF, U+00AD, U+180E) or a Unicode tag character (U+E0000-U+E007F) is `destructive`, "Command contains invisible or control characters". The same holds for the tool name, every path field and the URL. In a command also the Unicode blanks above count, because PowerShell splits words there and the lexer does not (`Remove-Item<NBSP>x` was one unknown word). On the headset every command string, path, URL and tool name shows these characters as visible escapes (`\r`, `\x1b`, `\u{202e}`; a newline as `\n`, since nothing in the bridge says the headset renders line breaks), escaped before the display is cut, so a field that grows past its cap by escaping is truncated and needs two hands. Argument arrays use their own `$'…'` rendering. Titles, plan steps, feed text, explanations and the agent's last action drop these characters.

**PowerShell typographic quotes and dashes.** PowerShell 5.1 reads U+2018-U+201E as quotes (also closed by an ASCII quote) and U+2013, U+2014, U+2015 as parameter dashes (tested). The lexer does not model them: text read as PowerShell (the PowerShell tool, non-Claude agents on Windows, `pwsh -Command` payloads) with any of them is `destructive`, "Complex shell syntax". Bash text is not affected.

**Paths: decided lexically, links never followed.** Whether a write leaves the project is decided from the cwd and the raw path. The file system is asked one thing only: whether a component below the cwd is a link, with `lstat` (never `realpath`, `stat`, `exists` or `readdir`). Before each call the path passes the impact check's local-path rules (`src/local-path.ts`): no UNC, device or drive-relative path, no control characters or Windows names the shells read differently, at most 4,096 characters, and none of the network or automount locations (macOS `/net`, `/home`, `/Network`, `/Volumes`, also under `/System/Volumes/Data`; Linux `/net`, `/mnt`, `/media`, `/run/user/<id>/gvfs`). A path it cannot decide counts as outside the project: a link on the way (also as the last component), a network location, a cwd that is not a local absolute path (on Windows a cwd needs a drive, so `/repo` or `/c/Users/…` is not one) or holds `.`/`..`, a failed lookup, or more than 128 lookups for one request. A missing component or a file ends the walk (nothing below it can be a link). POSIX takes `..` after the part before it was found to be a real directory; Windows folds `..` as written, as its path APIs do. The cwd itself is not looked at.

Known gaps (not detected, or detected only partly):

- **Exec vectors in program options (GTFOBins-style).** These are left out on purpose, because the denylist is frozen:
  - `ssh -o ProxyCommand=...`
  - `tar --to-command` / `--checkpoint-action=exec` / `-I`
  - `rsync -e`
  - `awk 'BEGIN { system(...) }'`
  - `sed 'e'`
  - `vim -c '!...'`
  - `gdb -ex 'shell ...'`
  - `zip -TT`
  - `less` / `man` shell escapes
- **Files written by options of read-style tools**, such as `find -fprint` and `strace -o`.
- **Remote commands.** `ssh host 'rm -rf ~'` is `network`; what runs on the remote host is not inspected.
- **Unknown and MCP tools** (`mcp__server__tool` and any tool name the classifier does not know) are `safe` unless the name contains a danger word (`delete`, `remove`, `drop`, `reset`, `force`, `rm`, ...) or their input carries a `command` or a path field (`file_path`, `path`, `target`, ...) that classifies higher. What such a tool really does is not inspected.
- **`PATH=` prepends** (`PATH=./bin:$PATH git status`, `$env:PATH = ...`) are not flagged. They give no capability beyond the script-file policy above.
- **Arithmetic indirection through a variable built at runtime** (`x=$(printf ...); (( x ))`) is not caught. A literal stored payload (`x='a[$(cmd)]'`) is caught.
- **PowerShell is a reduced dialect.** Here-strings (`@' ... '@`) are not modelled, and a bare `$(...)` statement is treated as obfuscated.
- **Lexer limits.**
  - `case ... esac` is classified `destructive` as a whole (its `)` pattern terminators cannot be tracked), so a legitimate inline `case` costs a two-hand confirmation.
  - Input the lexer refuses to guess about fails closed (`destructive`, "Complex shell syntax"):
    - an unterminated array subscript or compound assignment;
    - an array subscript containing an unquoted blank, newline, `$'...'` or shell metacharacter (`<` `>` `(` `)` `;` `&` `|`) (bash's rules for when `NAME[` starts a subscript are not modelled in full, so `x=1 if a[;cmd;]=1` and similar are treated as unknowable, even where bash itself would run nothing; this also makes plain arithmetic subscripts such as `a[1 << 2]=x` or `a[i>0]=x` cost a two-hand confirmation);
    - a heredoc inside `$(...)`/`<(...)`/`>(...)` whose terminator line is `DELIM` followed by text and a later `)` (bash 5.2 ends the heredoc there, older bash does not); `DELIM` alone and `DELIM)` are handled normally;
    - pathologically ambiguous `((` nesting (more than 64 failed arithmetic attempts in one command).
  - Elements of a compound array assignment (`a=(x y)`) are treated as data, as bash does; only their command substitutions and redirections are classified.
  - Extended globs and `{varname}>` redirects are not modelled.
  - Subshell `( cd x; ... )` scoping is flattened, which is conservative: the `cd` stays in effect afterwards.
- **`cd` and CDPATH.** A plain `cd name` resolves as `./name`. It becomes unknown (later relative writes count as outside the project) when the bridge process has a non-empty `CDPATH`, or when the command earlier sets CDPATH, or uses `source`/`.`, `eval`, `shopt`, `set -a`, `read`/`mapfile`/`readarray`, `printf -v`, or `declare`/`export`/... with a non-literal argument.
- **Perl debugger hooks.** `PERL5DB` / `PERL5DB_THREADED` environment variables and plain `perl -d` (which reads rc files) are not detected.
- **Repository config.** Git aliases and config already present in the repository (`.git/config`) are not read. Only `-c` flags, `GIT_*` variables and `git config` writes in the command itself are checked.
- **Links.** A link below the cwd makes a write count as outside, also when it points inside the project (a link to `.claude` now reads as "Writes outside the project", not as agent config). A link created later, outside the classified command, is not seen, and nor is one created by an earlier part of the same command (`ln -s /etc x; echo > x/y`, which is destructive anyway through `ln`). Links in the cwd's own path are not looked at; target and cwd are compared as written.
- **Lexical comparison.** Windows 8.3 short names (`PROGRA~1`) and other spellings of the same directory are not equated: such a path counts as outside (the more severe reading). macOS compares case-sensitively although APFS usually is not, with the same effect.
- **Network locations the rules do not name.** A mapped network drive or `subst` drive on Windows (`Z:\…`), an NFS or SMB mount at another place on Linux or macOS, and OneDrive placeholders pass the local-path rules, so an `lstat` on a component below such a cwd can reach a server or wake a sync provider. At most 128 calls per request.
- **Lookup budget.** A command with very many distinct write targets (more than 128 components to look at) counts as outside.
- **Argument arrays.**
  - The floor of the joined reading makes some arrays more severe than what runs (`["echo","a; rm -rf x"]` is destructive), and its reason may then name the joined reading.
  - An element starting with `~` counts as outside, although no shell expands it in an array.
  - Only invisible characters are escaped. Look-alike letters (Cyrillic `а` for Latin `a`) are shown as they are.
  - For an array whose elements alone are longer than 64 KB only the head is rendered, and `commandLength` is then a lower bound (every element plus one separator); it is beyond the length cap and cut anyway.
- **Known over-warnings.** A Windows cwd without a drive letter (`/repo`, Git Bash `/c/…`) makes every write destructive. Any CR makes a request destructive, also a multi-line command or a Codex patch with CR LF line ends. Typographic quotes or dashes in PowerShell text (German „…“ in a message) and the Unicode blanks in any command are destructive.
- **Not tested.** PowerShell 7's line breaks and blanks; `cmd` escapes and separators against the lexer (`cmd` itself was probed: `^` escapes `&` and `|`, `^^&` separates, `&` inside double quotes is literal, `&&`, `||`, `|` separate), other PowerShell look-alikes (only U+2018-U+201E and U+2013-U+2015 were tested; U+2212, U+2010, U+2011, U+FE63, U+FF0D are literal there), and how the headset renders the escapes.

## Recorder anonymisation: known gaps

Recordings must be reviewed by hand before they are shared.

- A glued quoted segment containing a space can leak its tail (`token="a"b'c d'`, `--token=abc"d e"`).
- Object values after auth/token/secret keys are over-redacted.
- Each session is anonymised against its first `cwd` (`<repo>`); `path` and `cwd` values outside that root and outside every home keep only their basename (`<abs>/a.ts`). Inside `command` and `summary` text such paths are kept as written (`cat D:\clients\x\a.ts`).
- Drive-relative paths (`C:clients\x`) and `file:///` URLs in `path` or `cwd` are not recognised as paths and are stored verbatim.

## Marshal itself is two-hand

An agent must not switch off the control that watches it with a one-hand approval. The classifier rates as destructive, reason "Changes or stops Marshal itself":

- every call of Marshal's CLI: `lotse` (also `lotse.cmd`, `lotse.ps1`, `lotse.exe`, with a path, quoted, through `npx`, `npm exec`, `pnpm dlx`, `yarn`, `bunx`), and `node` running a `cli.js` (or `cli`) in a path that names `lotse`, `bridge` or `marshal`, this bridge's own `dist/cli.js`, or any `cli.js` followed by `connect`, `disconnect`, `install-hooks` or `uninstall-hooks`, in both shell dialects and in argument arrays;
- the only exception is exactly one literal read-only word (`status`, `--help`, `-h`, `help`, `--version`, `-v`, `version`) with nothing after it, not reached through a wrapper that adds arguments (`xargs`, `parallel`, `find -exec`), not with command substitution, variables, globs, `@file` or splatting, and with stdin neither piped nor redirected. A bare `lotse` counts.

Writes below the agents' and Marshal's own folders count as "Changes agent or Git settings" also when the agent's working folder contains them (for example the home folder): `.claude`, `.codex`, `.gemini`, `.muse`, `.config/muse`, `.lotse`, besides `.git/hooks` and `.git/config`. Segment names are compared case-insensitively after dropping trailing dots and spaces and an alternate data stream suffix (`:name`), and any Windows 8.3 short-name segment (`CLAUDE~1`, `SETTIN~1.JSO`) counts as protected, since it is not resolved (no file-system call). Outside the working folder every write was already "Writes outside the project", and deleting is destructive anyway.

No text that reaches an agent (deny messages, halt refusals, replies) tells it how to disconnect, uninstall or stop Marshal; `test/agent-texts.test.ts` checks the strings.
